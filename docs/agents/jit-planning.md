# JIT planning

What stands between Fraze and a JIT backend, with MIR as the backend. Paths are relative to `compiler/source/fraze/`.

The backend is an off-the-shelf JIT library, which brings its own optimizations and portability. Writing a code emitter for Fraze is ruled out.

## Current state

- **Pipeline:** `Compiler::SetCodeGenerator(CodeGenerator::JIT)` makes `Compile` run `JITCodeGenerator` (`compiler/JITCodeGenerator.*`) instead of `VMCodeGenerator`, and return a `JITProgram` (`program/JITProgram.*`), which owns the MIR context and the machine code in it. Only the `.cpp` files and `JITCodeGenerator.h` include MIR's headers; `JITProgram.h` forward-declares `MIR_context`.
- **Generated so far:** every function in the program, a template once per instance, over `bool`, `int`, `num`, an enum, `string`, `object`, a class, an interface, a functor, an array and a struct, which `MIRTypeOf` maps to `I64`, `D` and `P`. MIR has no pointer register, so `NewRegister` puts a `P` in an `I64` one, while a parameter, a proto and a memory operand keep `P`. In a body: blocks, `return`, literals, a string literal, `null`, a default value, a cast, a check site, a type literal, `is`, `sizeof`, a fold, `new` of a class, an array or a struct, direct and extern calls, a call through an interface, a call to a functor, locals, statics, fields, elements, an array's count, enum members, assignment, every arithmetic, bitwise, comparison and logical operator, `int`/`num` conversions, unboxing, and `if`, `while`, `for`, `switch`, `goto` and a label. No `await` reaches the generator; see **Coroutines** below. Parameters and locals are MIR registers, named by index because Fraze allows shadowing and MIR rejects a repeated register name; `variableRegisters` maps each definition to its register.
- **Strings and asserts:** a string literal is allocated with a `PersistentAllocator`, so it is never collected or moved and its address goes into the code as an immediate, and `null` is the immediate 0. `assert` needs nothing of its own: `SemanticAnalyzer` lowers it to `Debug.Assert(condition, message, siteId)`, where the id comes from a `CheckSiteExpression` that the generator registers in `Program::checkSites` as `VMCodeGenerator` does. A string the GC owns comes from native code: a concatenation or a conversion to string lowers to a call into `String`, whose extern allocates the result.
- **Failures:** an exception out of native code reaches the host again. `common/jump/LandingPad.h` is a `thread_local` chain of pads, each pushed by its constructor and popped by its destructor; `JITProgram::InvokeImpl` opens one and saves a `JumpPoint` in its own frame before calling the static constructor and the invoked function, and the extern shim's `ApplyFunc` is the stub - it catches, stores the exception in the innermost pad, leaves the `catch`, then jumps, and the pad rethrows where native code can unwind normally. A shim with no pad above it rethrows instead, which is what happens when the VM calls an extern. No test fails on purpose, so this path runs only when a check does fail: a failing `assert` under `--jit --test` has to print its location and exit 1. A window callback into Fraze, which `Window.cpp` invokes from inside the `NativeWindow.PumpMessage` extern, is the case with two chained pads.
- **Statics:** a static is memory in `Program::globals` at the word offset `RuntimeTypeInfo` gave it, reached through a register holding `globals.data()` as an immediate - the array is sized before any body is generated, so that address is fixed for the program's life. `EmitVariableOp` returns a register for a local or parameter and that memory operand for a static, and `Visit(IdentifierExpression)` loads a static where it is read rather than passing the memory operand along, so a call later in the same expression can't change the value the expression sees. Each access emits its own base `MOV`, which GVN folds at the default optimization level and leaves alone at `Off`. Initialization needs nothing: a static's initializer is already a `VariableDefinitionStatement` in its owner's `$staticConstructor`, each of which the enclosing section's constructor calls, so running the global one covers them all.
- **Objects:** `new` of a class visits `NewExpression::allocExpression`, the analyzer's call to the `Type.NewClass` extern, whose argument is a `TypeLiteralExpression` the generator turns into the type's id. It then stores every field: its argument where the `new` passes one, and the field's own initializer otherwise. `EmitFieldOp` is the counterpart of `EmitGlobalOp`: a field is memory at `ClassDataOffset` plus the word offset `RuntimeTypeInfo` gave it, off a register holding the object, and `Visit(IdentifierExpression)` loads it where it is read, as it does a static. A method needs nothing of its own, since its receiver is argument 0 by the time the generator sees the call, and a null check is a call to an instance of `Debug.AssertNotNull<T>`. A compound assignment or a `++` on a field or an element evaluates its receiver twice, as the VM does (`known-bugs.md`). `Visit(VariableDefinition)` does nothing, because a definition is not code: a field's initializer is generated by each `new` that uses it.
- **Arrays:** `new` visits `allocExpression`, a call to `Type.NewArray`, and stores the elements it lists. `EmitElementOp` is a memory operand off the array at `ArrayDataOffset`, indexed by a register scaled to a word, and `.Count` reads the length word of the header. With bounds checks on, the analyzer wraps the array in a call to an instance of `Array.CheckBounds<T>` and, unless the index is a plain local or parameter, evaluates the index into the temp of a fold, so `Visit(FoldExpression)` came with arrays: it visits the statements and takes the last one's expression as its value.
- **Structs:** a struct's value is the address of its storage, so `MIRTypeOf` gives it `P` and one path serves a struct wherever it is.
  - **Storage:** a local, a `new`, a default value, a by-value argument and a call's result each get storage from `NewStructStorage`, an `ALLOCA` prepended to the function so that it runs once per call rather than once per pass through a loop. A struct in a static, a field or an element is in place there, and `EmitAddress` turns that memory operand into its address.
  - **Moves:** `EmitMove` stores a value of any type, and for a struct copies it a word at a time, which is what a local's definition, an assignment, a field or element initializer and a `return` all go through. `EmitLoad` is its counterpart, and for a struct yields the address instead of loading.
  - **Calls:** a struct parameter is an address either way. By value, the caller copies the argument into storage of its own and passes that, so the callee is free to change it; by reference, which is what a struct method's `this` is, it passes the address it has. A struct result goes into storage the caller passes ahead of the parameters, kept in `resultStorageReg`, and the function has no MIR result. An extern follows the same shape, through `CallWithResultStorage`, except that it is passed the caller's own struct with no copy, since an extern never changes an argument. With the copy, the demo's per-vertex `Mat4` externs took most of a frame's work.
  - **Limits:** every site that makes a struct has its own storage for the whole call, so a function's frame grows with the number of such sites, and MIR emits no stack probe for a frame over a page. An array of structs divides the header's length and multiplies the index by the struct's size in words.
- **Interfaces:** an interface reference is the object's address, so a conversion to or from one generates nothing. A call dispatches where `VMCodeGenerator` emits `CallVirtual`: the callee has an implicit `this` and `arguments[0]` is typed as an interface.
  - **The call:** an interface call makes the lookup `Execute_CallVirtual` makes. `EmitInterfaceCalleeOp` emits a call to the `$getInterfaceImplementationAddress` runtime helper with the receiver, the interface's id and the interface function's `FunctionInfo::offset`. The helper calls `Class::GetFunctionID` and returns that function's `FunctionInfo::functionAddress`, and the `MIR_CALL` that follows takes the returned register as its callee, under the interface function's proto.
  - **Function addresses:** after `MIR_link`, `Visit(ASTRoot)` stores every generated function's `MIR_func::call_addr` in `FunctionInfo::functionAddress`. `call_addr` is the address of the code itself, while an item's `addr` is a thunk that jumps there.
  - **Bodiless functions:** an interface's functions are `isAbstract`, a functor's `invoke` among them, and `Visit(FunctionDefinition)` skips them.
- **Functors:** the analyzer does the work. A functor literal, and a function used as a functor, are each already a `new` of a functor class cast to the functor's interface, and a call to a functor already has the functor as its first argument. `Visit(CallExpression)` only has to take the callee from the functor interface's `invoke`, which makes the call an interface call. `VMCodeGenerator` also handles a call whose target is typed as a functor class, which the JIT rejects, because no source reaches it: the analyzer fails on a call to a functor literal and on a call through a `var` local that holds one.
- **Type tests and boxing:** the analyzer does most of this too. `typeof` is a call to `Type.Find`, an `is` or `as` on a reference is a call to `Type.IsInstance` or `Type.AsInstance`, and a `bool`, `int` or `num` that becomes an `object` is a `new` of its box class, `Boolean`, `Integer` or `Number`. Three things are left for the generator: `EmitConversion` unboxes by loading the box's only field, an `is` on a value that can't be null is a constant, and so is `sizeof`.
- **Generic types:** a generic class, struct or interface is generated once per instance, and an instance is an ordinary definition by the time the generator sees it. The generator only skips the template declaration, as `VMCodeGenerator` does, in `Visit(ClassDefinition)`, `Visit(StructDefinition)` and `Visit(InterfaceDefinition)`. A property and a constructor need nothing either: the analyzer lowers a property to calls to its `get` and `set` functions, and `new` of a class with a constructor to a call to it.
- **Expressions and conditions:** every expression leaves its value in `exprValueOp` and every condition is a `BT`/`BF` on that value, so there is one emission path and no equivalent of `VMCodeGenerator`'s branch lists - MIR's own `BLT`/`DBEQ` forms are left to its optimizer. `&&`, `||` and `?:` are branches into a result register, since the right operand must not run when the left decides. `EmitArithmetic` maps an operator and its operand type to one instruction, taking each compound assignment as its plain form, with two exceptions: `num %`, which MIR has no instruction for, calls the `$fmod` runtime helper the same way an extern is called, and `&?` masks and compares. The masked comparison is the VM's `> 0`, which reads a mask of the sign bit as unset.
- **Labels:** a MIR label is an insn created before it is positioned, so a forward `goto` needs no patching: `labelInsns` holds one per `LabelStatement`, created by whichever of the label and its first `goto` the generator reaches first, and cleared per function. A `switch` follows `VMCodeGenerator`'s rule, a table when the case span is under twice the case count and a comparison chain otherwise; `MIR_SWITCH` has no entry outside its table, so an unsigned `UBGE` sends everything out of range to the default.
- **Externs:** a call goes straight to a `static` shim per extern, `ExternalFunction<Func>::JITEntry::Call`, reached through `IExternalFunction::GetJITEntry`. `JITParam` and `JITResult` (`common/ExternalFunction.h`) give it a signature of scalars and pointers only: `Program*` leads whether or not the C++ function takes one, a struct or object parameter arrives by address, and a `Boolean` result is widened to `Integer`, so MIR sees no aggregate and no result needs extending. An object crosses as the `Object*` that compiled code holds, and the shim casts it to and from the C++ class, because a class with virtual functions, `TypeInfo` among them, keeps its `Object` part at an offset. A struct result goes to `CallWithResultStorage`, which constructs it in storage the caller passes. The generator builds the MIR signature from the Fraze types alone, so the two halves have to agree - the C++ half covers every registered extern, while the generator's half passes a scalar, a reference of any kind, and a struct by address, a struct result included. Each extern is an import in `importedFunctions`, which also holds the generator's own runtime helpers, and is kept out of `functionItems` because `MIR_load_external` binds an import's address by name instead of resolving `ref_def`. The program is an immediate operand holding the `JITProgram`'s address, which the code that passes it can't outlive.
- **Extern classes:** nothing in the generator is specific to one. `new` of an extern class is a call to its constructor by the time the generator sees it, with no `new` left to pass as a receiver, and the constructor's native allocates the object and returns it. So a constructor is an extern call like any other, an overload included, since an import is named by `GetFunctionName` and each overload has its own name. A function of the class is an extern call whose receiver is argument 0. An extern class has no field for `EmitFieldOp` to reach, because the parser accepts only extern functions in one. Compiled code holds the `Object*` the constructor returned, which points 8 bytes into the object when its C++ class has virtual functions, and `Heap::Mark` finds the allocation from it as it does from any interior pointer. `is` and `as` need nothing either: `Type_IsInstance` and `Type_AsInstance` compare `ClassInfo` ids, and nothing reads `ClassInfo::isExternal`.
- **Coroutines:** nothing in the generator is specific to one either. The analyzer lowers a coroutine to a task class whose `Resume` function switches on `$position` and jumps to the label after the `await` it suspended at, so the generator sees a class, a `switch`, a `goto` and calls through the `Awaiter`, `Awaitable` and `Task<T>` interfaces. An async extern is an extern call whose first argument is its task, which the shim passes like any object. Its native finishes the task later, from the `Dispatcher`, by invoking `OnAwaitableCompleted`, which is a call from the host with an argument.
- **Type info:** `Visit(ASTRoot)` builds `RuntimeTypeInfo` the way `VMCodeGenerator` does, so `Program::typeInfo` and the fixed-address `globals` array are populated and an extern's parameter and result sizes are checked against its C++ types; the VM frame offsets it also assigns go unused.
- **Names:** a MIR item name is `qualifiedName#id`, where the id is the function's `TypeInfo::id`, since overloads share a qualified name and MIR item names must be unique. `FunctionDefinition::GetSignature` doesn't tell every pair of overloads apart: a member function's receiver is its first parameter, so `num Angle(Vec3 v)` and `static num Angle(Vec3 a, Vec3 b)` in `Vec3` have one signature. `functionItems` is keyed on the function's `Type*` for the same reason, and `protoItems` on the MIR signature, so one proto serves every function that shares it. A call references a forward item, because MIR allows only one open function at a time, and MIR resolves it when the module is loaded.
- **Optimization:** `Compiler::SetOptimization` takes an `Optimization` level that maps to `MIR_gen_set_optimize_level`, and the VM code generator ignores it. The demo's `--jit` sets `Optimization::Maximum`, so no command runs the other three levels.
- **Running:** nothing is generated for a call from the host. `Program::Invoke` knows the C++ type of each argument at its call site, so it hands `InvokeImpl` the argument words and the instance of `CallCompiledFunction` (`program/Program.h`) for those types, which makes the typed call. `JITProgram::InvokeImpl` finds the function by qualified name through `Program::GetTypeInfo`, as `VMProgram` does, so the first function with that name wins, and calls through that instance with the function's `FunctionInfo::functionAddress`. `FunctionInfo::compiledResultKind`, which the generator sets, says whether the result is nothing, an integer or a num, and marks a function that takes or returns a struct, which a host can't invoke. The call trusts the host's argument types to match the function's parameters, as the VM does: both check only how many there are. Before the first call `InvokeImpl` makes the calling thread the heap's execution thread and runs the global `$staticConstructor`, as `VMProgram` does.
- **GC roots:** `Heap::RegisterExecutionThread` records the execution thread, which is the one thread that runs Fraze code - a handle that can suspend it and read its context, its id and its stack base - and `Heap::CollectInternal` scans the execution thread's native stack and registers before the roots it already had. `GetUsedStackRange` is the VM's answer for its `Word` stack and stays empty in `JITProgram`. The VM gets the native scan too, which can only retain more.
  - **On the execution thread** nothing is suspended: `SaveJumpPoint` captures the non-volatile registers into the collector's own frame, and the scan runs from the stack pointer it saved to the stack base.
  - **On any other thread** the collector suspends the execution thread, takes `GetThreadContext`, scans the context and the stack from its `Rsp`, marks every other root, and resumes it before sweeping. `SuspendThread` only requests the suspension, and `GetThreadContext` is what waits for it.
  - **The context is captured with `CONTEXT_FULL | CONTEXT_XSTATE`,** because `CONTEXT_FULL` stops at `xmm` and a reference can sit in the upper half of a `ymm` or `zmm` register. `RegisterExecutionThread` allocates the buffer, at the size `InitializeContext` reports, and the collector zeroes it and lays it out again before each suspension. The AVX-512 part of the mask is untested, for want of a machine that has it.
  - **Nothing between the suspend and the resume takes a lock or allocates.** In a Debug build creating or destroying a `std` container's iterator takes the global `_LOCK_DEBUG`, which deadlocks within seconds once the suspended execution thread can be holding it. So nothing a collection reads is a `std` container: `Heap` keeps its pages and ranges in `fraze::vector` (`common/Vector.h`) and its pinned set in `fraze::hash_set` (`common/HashSet.h`), whose iterators hold no debug bookkeeping, and `Page` keeps its per-block arrays in `dynamic_array`.
  - **`Heap::Allocate` asserts** that an unpinned allocation comes from the execution thread.
- **Testing:** nothing is specific to the JIT. The demo's `--jit` flag only switches the code generator, so `--jit --test` runs `RunAllTests` and `MathTests.Run` with the JIT, `demo\RunScene.ps1 -JIT` runs the scene with it, and the bytecode VM runs the same tests without the flag. Every check is an `assert`, so `--jit --test` proves nothing in a build that calls `DisableAssert`, since the checks are then never generated. Three things have no test: the path a failure takes back to the host, which runs only when a check fails; a call from the host that passes a num or takes back a num or a bool, since the demo passes references and ints and reads only the int `main` returns; and how much a collection frees.
- **Errors:** MIR calls `ThrowMIRError`, which throws a `fraze::Exception` located at the node `JITCodeGenerator` is visiting, so a repeated item name, a wrong operand mode or a proto that doesn't match its call reports like any other compile error. An error out of `MIR_finish_func`, which validates a whole body at once, can only point at the function. The error func is a field of the context, so `MIRContext` installs the handler in its constructor, where a new context would otherwise keep MIR's print-and-exit default.
- **Memory:** `MIRContext` owns the context and both allocators it is created with. Nothing in MIR allocates outside them, so the destructor releases everything MIR allocated and `MIR_finish` is never called. `JITProgram` owns the context from construction, and `Visit(ASTRoot)` keeps the program itself local until generating has fully succeeded, so a throw anywhere in generation releases both and needs no handler. `realloc` moves a block, hence `intrusive_list::relink_neighbors`.
- **Forwards:** a call references a forward item, so a call to a function the generator never defines leaves one unresolved, which spins `MIR_link` instead of reaching `ThrowMIRError`. `Visit(ASTRoot)` checks `ref_def` on every item in `functionItems` before loading the module, because `add_item` sets it on both items as soon as a forward and a definition share a name, whichever came first. An import is not in `functionItems`, so the check skips it and `MIR_load_external` resolves it.
- **Reference material absent from `third_party/mir`:** `MIR.md` and `CUSTOM-ALLOCATORS.md` ship only in a full MIR checkout. `MIR.md` documents the error func as `(MIR_context ctx, MIR_error_type_t, const char *message)`, which is stale - both 0.2 headers declare `(MIR_error_type_t, const char *format, ...)`. There is no `ctx` parameter, which is why `ThrowMIRError` reads the location from a file-static. No tool in the MIR tree calls `MIR_set_error_func`, and nothing in it handles a node whose storage moved.

## Already compatible

- **Globals** live in `Program::globals`, a fixed-address array, which the JIT addresses directly; see **Statics** under **Current state**.
- **Static initialization** is ordinary functions: the global section's `$staticConstructor` is the entry point.
- **Coroutines** are lowered to task classes driven by a `$position` switch, so nothing needs stack switching.
- **Runtime checks and allocation** are calls (`Wrap*` helpers, `Type.NewClass`), not special opcodes.
- **Dynamic dispatch** exists only for interface calls.

## MIR on Windows

Windows x64 isn't an official MIR target: the Windows ABI is implemented but minimally tested ([discussion](https://github.com/vnmakarov/mir/discussions/345)). MIR builds as a static library with MSVC v143 (MIR's generated `projects/mir.vcxproj`, which defines `MIR_PARALLEL_GEN`). Checked in Debug x64:

- **Works:**
  - eager generation (`MIR_set_gen_interface`);
  - compiled code calling C functions, varargs included, and C++ functions taking and returning `double`;
  - the host calling compiled code, and host → compiled → host → compiled reentrancy;
  - a `longjmp` through compiled frames when the jump buffer's `Frame` field is cleared after `setjmp` (`reinterpret_cast<_JUMP_BUFFER*>(&buffer)->Frame = 0`), which makes it restore registers without unwinding. Compiled code still runs correctly afterwards;
  - the landing-pad scheme under **Failures** below, including two chained pads across two compiled segments, run twice in a row.
- **Fails:**
  - a C++ exception thrown by a host function called from compiled code ends the process with `0xC0000409` instead of reaching the host's `catch`;
  - a plain `longjmp` through compiled frames, once a C++ `catch` has run, ends the process with `0xC00000FF` (`STATUS_BAD_FUNCTION_TABLE`): MSVC's x64 `longjmp` unwinds, and the unwinder rejects a frame it has no unwind data for.
- **Measured again on 2026-10-10,** because the first probe's source was gone and the result is load-bearing. Thirteen variants, each in its own process, over one compiled frame and over two with a dozen values live across the call:
  - `setjmp` is `_setjmp` in this toolchain (`setjmp.h` defines it so unless `setjmpex.h` is included), and `_setjmpex` behaves the same in every variant, so the lightweight-versus-SEH distinction is not the lever it looks like.
  - a plain `longjmp` with no exception in flight survives every frame shape tried, including frames holding code addresses in spill slots. That is luck, not support: a PC with no unwind data is taken for a leaf, so the unwinder crawls the stack 8 bytes at a time and happens to find the target frame. A simple test of this therefore proves nothing.
  - with `Frame` cleared it is fatal to `longjmp` from inside a `catch` block (`0xC0000005`), and safe to jump after leaving one.
  - with `Frame` left alone, an unwinding `longjmp` runs the destructors of locals in the pad's own frame and then resumes in that frame, leaving destroyed objects in scope.
- **The CRT's pair is no longer used.** `common/jump/JumpPoint.h` and its `.x64.asm` are `SaveJumpPoint` and `JumpTo`, which save and restore what the Win64 ABI calls non-volatile - the integer registers, `xmm6`-`xmm15`, `MXCSR` and the x87 control word - plus the stack and instruction pointers, and nothing else. The stack never changes, so the TIB's stack and fiber fields are left alone, which is the part of `boost::context`'s `jump_x86_64_ms_pe_masm.asm` that doesn't apply here. Both functions have an empty prologue declared with `FRAME` and an immediate `.endprolog`, so a stack walk through `SaveJumpPoint` is described rather than guessed. The same probe says they carry the whole scheme through two fat compiled frames with `MXCSR` and live doubles intact, and that with them a jump from inside a `catch` is no longer fatal - a later throw still works - though the exception object is still leaked, so a stub should store it, leave the `catch` and then jump.

The failures have one cause: Win64 unwinding requires registered unwind data (`RtlAddFunctionTable`) for every frame it walks, and MIR emits none. That also stops debuggers and profilers walking compiled frames.

The whole program is compiled up front. Lazy generation isn't used, and on Win64 it crashes on the first call.

## Blockers

- **Untyped bytecode.** Loads and stores (`PushLocal`, `PushArgument`, `PushWord`, `PopGlobal`, ...) move untyped words. MIR keeps integer and floating-point registers apart and has no bitcast, only value conversions, so translating bytecode would need a type on every load and store. Stack-only operations (`Dup`, `DupN`, `Pop` counts, the return storage a caller reserves) have no register equivalent.
- **Calling convention.** Done for direct calls; see **Structs** under **Current state**. VM frames keep arguments below `rbp`, and the caller reserves return storage that `Return` copies into. A native convention needed:
  - typed parameters;
  - structs passed and returned by address (MIR returns only a few values in registers, and `Mat4` is 16 words);
  - memory (`ALLOCA`) for any local whose address is taken (`PushLocalAddr`, `ref` parameters, struct receivers passed by reference).
- **Call targets.** `Call` and `CallExternal` carry a `typeInfo` index that the VM resolves at run time; a JIT resolves direct calls when compiling. `CallVirtual` goes through `Class::GetFunctionID`, a linear scan of the class's interfaces that returns a function id, then through `typeInfo` to `codeStart`. The JIT makes the same lookup through a runtime helper; see **Interfaces** under **Current state**.
- **Externs.** Done, through the shim under **Current state**: scalars, references, structs, extern classes and async externs. Why a struct goes by address:
  - **Aggregates are argument-only.** `MIR_T_BLK` through `MIR_T_RBLK` "can be used only args" (`mir.h`), and the five `BLK` variants encode a C ABI's register classification, so passing a struct by value needs the variant the callee's ABI expects, and returning one needs `RBLK` (the address of return storage) or an explicit pointer parameter. Passing every struct by address avoids the classification entirely.
- **Host entry.** Done; see **Running** under **Current state**. `VMProgram::InvokeImpl` builds a VM frame from a `Word` array.
- **GC roots.** Done; see **GC roots** under **Current state**. `Heap::CollectInternal` scanned `Program::globals`, `Program::GetUsedStackRange()`, the ranges registered through `Heap::AddRange` and the pinned set, and compiled code appears in none of them: its references sit in registers and on the native stack. What made that a wiring problem rather than a redesign is that the collector is already conservative and non-moving - `MarkRange` walks a range a word at a time and `Mark` validates each candidate by alignment, `FindPage` and `Page::GetAllocationStart`, which also maps an interior pointer back to the allocation holding it, so a word that only looks like a pointer costs a retention and nothing ever has to be updated after marking. A collection can also start on the worker thread (asset loading allocates through `ScopedAllocator` on it) while the execution thread is running, because `Heap::AllocateRaw` collects as soon as the existing pages can't satisfy a request.
- **Failures.** Done; see **Failures** under **Current state**. `Debug.Fail`, `ENFORCE` and any extern can throw, and the pads and stubs carry it back to the host.
- **VM-only diagnostics.** Per-operation source locations drive the heap debug locations, `FRAZE_PRINT_EXECUTED_CODE` and `ExportBytecode`; compiled code has none.

## Recommended approach

- **Generate MIR from the lowered AST,** with a second `ASTVisitor` beside `VMCodeGenerator`, rather than translating bytecode. The AST is typed and fully lowered, so the generator is mechanical. Whether the bytecode VM stays, as a reference or debug backend, is undecided.
- **Externs:** done, as the per-extern shim under **Current state**. A bridge through `IExternalFunction::Invoke`, taking a block in the VM stack's layout, was the alternative and is now unnecessary. A direct call to the registered C++ function is not possible: it takes each scalar as `const T&` into the VM's stack words, so MIR would need an address per argument.
- **Host entry:** done, as the `CallCompiledFunction` template under **Running** in **Current state**.
- **GC:** built, and described under **Current state**. The design: stop the world by suspending the execution thread, the one thread that runs Fraze code. Fraze is single-threaded and native code that holds an object pins it (`native-interop.md`), so the roots are the globals, the pinned set, and the execution thread's stack and registers. A collection the execution thread starts for itself needs no suspension: its own stack pointer plus `SaveJumpPoint` is enough, because a reference the compiled frame held in a volatile register was spilled to that frame before it called into the allocator, and a non-volatile one is either still in the register or saved in a callee's prologue area. A collection another thread starts suspends the execution thread and takes `GetThreadContext`, which is needed there because a thread stopped mid-expression can hold a reference in any register. `Heap` keeps one execution thread - a handle duplicated from `GetCurrentThread` with `THREAD_SUSPEND_RESUME | THREAD_GET_CONTEXT`, and the stack base from `GetCurrentThreadStackLimits` - and asserts that an allocating thread is either the execution thread or pinning. Between the suspend and the resume the collector must take no other lock, since the suspended execution thread may hold the CRT heap or loader lock, which rules out the `FRAZE_HEAP_DEBUG` logging and growing a page inside that window.
  - **Safepoint polling was considered and rejected.** It is what HotSpot and .NET do, but they need the mutator at a known instruction because their collectors move objects and need precise root maps there. This collector is conservative and non-moving, so it only needs bytes to scan, and `GetThreadContext` gives those as well as a poll site would - without a check in the interpreter's hottest loop, poll sites in generated code, the latency of a Fraze loop that calls no externs, or a rule against native code blocking on an allocating thread. That trade depends on the collector staying conservative and non-moving: a moving collector, or precise stack walking of compiled frames, brings safepoints back with it.
- **Failures:** built, and described under **Current state**. The design, which needed nothing from MIR: C++ exceptions travel only through native segments of the stack, and `JumpTo` crosses the compiled segments.
  - **Landing pads:** every native → compiled edge is one: host entry, an extern calling back into Fraze, interpreter → compiled. It does a `SaveJumpPoint`. On landing, it restores whatever state the backend keeps (the VM's `rsp`, `rbp` and `rip`; the JIT has none) and rethrows the exception the stub stored in the pad.
  - **Stubs:** every compiled → native edge is one: extern, runtime helper, compiled → interpreter. It catches all exceptions, stores `std::current_exception()` in the innermost pad, leaves the `catch`, then calls `JumpTo` on it. The extern shim in `ExternalFunction` is the one stub that covers every extern, `Debug_Fail` among them. A native function compiled code calls directly, with no stub - today `$fmod` and `$getInterfaceImplementationAddress` - must not throw.
  - **Pad chain:** pads form a `thread_local` chain, since a jump buffer holds stack addresses, and each one pops itself before rethrowing.
  - **Constraints:**
    - A stub stores the exception, leaves the `catch`, and only then jumps. Jumping from inside the `catch` leaks the exception object, and does worse than that with the CRT's `longjmp`.
    - Keep the function that saves a point minimal: `volatile` for locals changed after `SaveJumpPoint`, and nothing above it may return while jumps to it are still possible.
    - Nothing here is linked `/CETCOMPAT`. If it ever is, `JumpTo` must also unwind the shadow stack (`incsspq`).
  - **Cost:** a `try` in a stub costs nothing until something throws. Each landing pad is a `SaveJumpPoint` into a 256-byte `JumpPoint`, which only matters if native → compiled entries are hot.
  - **Later:** the scheme extends to a Fraze `try`/`catch`, where a `try` becomes a landing pad, like Lua's `pcall`. Landing pads also fix the known bug where a `Program` can't run again after an exception escapes it.
