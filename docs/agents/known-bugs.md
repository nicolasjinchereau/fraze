# Known bugs

Unfixed bugs, each confirmed against the code or by a probe. Remove an entry when it's fixed. Paths are relative to `compiler/source/fraze/`.

- **Duplicate functor captures:** a functor literal whose body names the same captured variable twice fails with "multiple definitions found". `Parser::GetCaptures` returns one entry per occurrence, and `ParseFunctorExpr` adds a field for each.
- **Compound assignment evaluates its target twice:** `a[F()].x += 1` calls `F()` twice, because `VMCodeGenerator::Visit(AssignExpression)` evaluates the left side to read it, and the store evaluates its receiver again.
- **`.Count` and `.Size` on a null array aren't null-checked:** `SemanticAnalyzer::Visit(IdentifierExpression)` lowers them to an `ArrayCountExpression` and an `Array.GetSize` call without `WrapWithNullCheck`, so a null array is read through instead of failing a check.
- **Ternary arms aren't checked against each other:** `SemanticAnalyzer::Visit(TernaryExpression)` checks only the condition, and the expression takes the true arm's type, so `true ? 1 : "str"` compiles.
- **A `Program` can't run again after an exception escapes it:** `VMProgram::InvokeImpl` restores `rip`, `rsp` and `rbp` only on a normal return. The demo exits after catching one, so this matters only to a host that catches and continues. The landing pads in `jit-planning.md` would fix it.
- **A functor literal can only be called through a functor-typed variable:** calling one where it is written, `(functor int() { return 7; })()`, fails with "expression cannot be evaluated", and calling a `var` local that holds one fails with "no definition found". `VMCodeGenerator::Visit(CallExpression)` has a branch for a target typed as a functor class, which neither form reaches.
- **An extern class's destructor never runs:** `Heap::CollectInternal` frees a dead object's blocks with `Page::Deallocate` and nothing else, and no other code destroys an object the heap holds. So the demo's `~Window`, `~Graphics`, `~Shader`, `~Texture` and `~Buffer` never run, and neither do the destructors of their members, such as a `ComPtr`.
- **`new` of an extern class that has no constructor compiles:** `new Type{}` finds no `#this`, so `SemanticAnalyzer::Visit(NewExpression)` lowers it to `Type.NewClass` like a `new` of any class. That allocates a `Class` with no fields under the extern class's type, which an extern function would then take for the C++ object.
- **A type name can resolve to a function:** inside a class, a type specifier whose name a member function also has resolves to that function's type, not to the class of that name in an enclosing scope, and nothing rejects it. Seen on an extern's parameter, where it surfaces as "External function parameter mismatch".
