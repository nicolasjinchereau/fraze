# Native interop

How C++ and Fraze call into each other. The compiler's own externs are registered in `Compiler::AddFrazeRuntime` and implemented in `compiler/source/fraze/compiler/NativeFunctions.h`; the demo's are registered and implemented in `demo/source/ExternFunctions.cpp`.

- **Extern functions:** a Fraze `extern` declaration binds by qualified name to a C++ function registered with `Compiler::AddFunction<&fn>("Section.Name")`. The function is a template argument, so the VM's call into it is direct and can be inlined. An overloaded name also takes a signature, the return type followed by the parameter types, each named in full (e.g. `"NativeBuffer(object,BufferType,BufferUsage,BufferCPUAccess,int)"`). A name registered without a signature is found first, for every overload of it. The C++ function may optionally take `Program*` as its first parameter, which the VM supplies and which isn't a Fraze parameter. An instance method receives its receiver as `Object& self`, or as a reference to the C++ class behind an extern class (`const TypeInfo& self`). A C++ struct passed or returned must occupy as many words as the Fraze struct it stands for, or the compile fails with a size mismatch. A native must not change a struct it is passed, because the JIT passes the caller's own struct and not a copy.
- **Extern classes:** `extern class NativeX { extern this(...); }` is backed by a C++ class deriving from `Object`. Its constructor, registered as `NativeX.this`, returns the `Object*` it allocates with `allocator.NewExternClass<CppType>("NativeX", args...)`. An extern class holds extern functions only, so it has no fields in Fraze. Nothing runs the C++ destructor (`known-bugs.md`).
- **Allocating from C++:** use a `ScopedAllocator`, which pins what it allocates until it's destroyed. Of native code, the GC scans only the stack and registers of the execution thread, which is the thread that runs Fraze code, so an object held anywhere else - on another thread, or in a closure posted to one - must stay pinned (`Program::PinMemory`/`UnpinMemory`) until Fraze can reach it. `Heap::Allocate` asserts that an unpinned allocation is made on the execution thread.
- **Async externs:** the C++ side of an `extern Task<T>` function receives the task object (`Class& task`) as its first argument, and takes `Program*` ahead of it to pin the task and invoke the completion. It pins the task, does its work (the demo loads assets on `WorkerThread`), then posts to the main thread's `Dispatcher` an action that sets the task's `$value` and `$position = -1`, calls `program->Invoke("OnAwaitableCompleted", task)` and unpins it. `WaitAsync` and `YieldAsync` in `NativeFunctions.h` are the minimal examples; `Texture::CreateTextureAsync` in `demo/source/Texture.cpp` is a full one. Posted completions only run when the demo's frame loop in `Main.fz` reaches its `await YieldAsync()`.
